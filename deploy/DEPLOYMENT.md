# Deployment — TAPAS Growth Autopilot (Linux / systemd)

Release 1.2 deployment checklist, restore and rollback.

## Install (first time)

1. Clone the repo and create the virtual environment; install `requirements.txt`.
2. Create `.env` from `.env.example`; set `TOKEN_ENCRYPTION_KEY` (Fernet), provider app credentials and `GEMINI_API_KEY`. `.env` is mode 600 and never committed.
3. Run the offline tests: `.venv/bin/python -m unittest test_smoke` and `.venv/bin/python -m unittest test_v12_reliability` — both must pass (run each in its own process; each suite sets a hermetic environment before importing the server).
4. Install the units:
   - `sudo cp deploy/tapas-growth-backend.service deploy/tapas-backend-watchdog.service deploy/tapas-backend-watchdog.timer /etc/systemd/system/`
   - Copy `deploy/watchdog.sh` to the path named in the watchdog unit and `chmod +x` it.
   - `sudo systemctl daemon-reload`
   - `sudo systemctl enable --now tapas-growth-backend tapas-backend-watchdog.timer`
5. Verify: `curl http://127.0.0.1:8000/api/health` returns `"ok":true` with `"version":"1.2.0"`, `"scheduler_running":true` and the scheduler job ids; `curl http://127.0.0.1:8000/api/status` shows the connected providers.
6. Chaos check (once per deployment): `kill -9` the uvicorn process; within ~15 seconds `systemctl show tapas-growth-backend -p NRestarts` must have incremented and `/api/health` must answer again.

## VM replacement / host rebuild

`/etc` does not survive a VM replacement; the home directory does. Keep the unit files, watchdog and a restore script in the workspace (home), and re-run the restore script after any replacement. The restore script:

1. Copies the three unit files into `/etc/systemd/system/`.
2. Regenerates the root-only egress-proxy env file (mode 600) from the restoring session's environment, when the network requires a proxy. Proxy values are copied by variable name only and never written into the workspace or this repo.
3. `systemctl daemon-reload`, enables and starts the service and the watchdog timer, and prints the health response.

## Monitoring

- Service logs: `journalctl -u tapas-growth-backend` (startup line reports version, scheduler jobs and missed-schedule count).
- Watchdog: probes `/api/health` every minute; outcomes append to its status log; two consecutive failures restart the service and append an ALERT line to its alert log.
- Health contract: `GET /api/health` → `ok`, `version`, `uptime_seconds`, `gemini_configured`, `scheduler_running`, `scheduler_jobs`.

## Rollback

- Code: the previous release is tagged `v1.1` in this repository. Check out that tag in the working copy and restart the service (`systemctl restart tapas-growth-backend`). The v1.2 database change is additive (one nullable `expires_at` column on `approval_queue`); v1.1 code ignores it, so no data migration is needed to roll back.
- Service: to return to manual operation, `systemctl disable --now tapas-growth-backend tapas-backend-watchdog.timer`, then start the backend with the launcher as before. (Not recommended — manual operation is the failure mode 1.2 exists to fix.)
- Verify after rollback: `/api/health` answers and `/api/status` shows the providers connected.

## Known limits (honest)

- The watchdog detects an unresponsive process; it cannot detect a host that is fully down. Boot recovery is systemd's `WantedBy` enablement.
- If the runtime rotates the egress-proxy credential while the host lives, provider calls fail until the proxy env file is regenerated by re-running the restore step; local endpoints keep working.
- X analytics is limited by the X account's API credit balance (X returns HTTP 402); this is an account state, not a deployment fault.
